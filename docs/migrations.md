# Проверка миграций

## Цепочка изменений схемы

| Ревизия | Изменение |
| --- | --- |
| `20260912_0001` | Создание продавцов, покупателей, аукционов, лотов, продаж и доходов |
| `20260917_0002` | Добавление аккаунтов и связей с участниками |
| `20260917_0003` | Добавление заявок на покупку и истории рассмотрения |

`make check-migrations` проверяет, что существует одна линейная цепочка не менее чем из трёх ревизий. При добавлении очередной миграции она автоматически включается в проход до `head`. Сценарий контрольных данных опирается на схему первой ревизии; при изменении исторической схемы его нужно согласовать с миграциями.

## Чистая БД

1. Создать новую БД из `template0` с уникальным именем.
2. Убедиться, что пользовательских таблиц нет.
3. Применить всю цепочку `upgrade head`.
4. Проверить текущую ревизию и выполнить `alembic.command.check`: автогенерация не должна предлагать изменения относительно моделей.
5. Повторить `upgrade head` и проверить, что данные не изменились.

## БД с данными

1. В другой новой БД применить первую ревизию.
2. Создать продавца, покупателя, аукцион, доступный и проданный лоты, продажу и доход.
3. Перед каждой следующей миграцией сохранить все значения прежних колонок всех предметных таблиц.
4. Применить очередную миграцию и сравнить записи: ID, связи, суммы, статусы, строки и временные отметки должны сохраниться.
5. После ревизии аккаунтов добавить связанный аккаунт со случайным паролем, сохранённым как PBKDF2-хеш; после ревизии заявок добавить pending-заявку.
6. На `head` проверить соответствие моделям через Alembic и повторное применение миграций без изменения данных.

При появлении новых колонок проверка сохранности сравнивает прежние колонки, поэтому добавление поля само по себе не считается повреждением данных. Правила заполнения нового поля необходимо покрывать отдельными тестами соответствующей функции.

`alembic.command.check` использует возможности автогенерации Alembic; это не полная проверка всех особенностей PostgreSQL. Бизнес-ограничения дополнительно проверяются интеграционными тестами приложения.

## Изоляция и права

Обе временные БД называются `auctions_migration_<UUID>_test`, их владельцем назначается тестовая роль. Сценарий не выполняет downgrade, очистку таблиц или удаление рабочей/обычной тестовой БД. Alembic получает явное соединение с временной БД через `Config.attributes["connection"]`; обычный `make migrate` продолжает использовать настройки приложения.

Административное подключение выбирается из `SETUP_DATABASE_URL` либо от имени текущего пользователя ОС на том же сервере. Оно должно иметь права создания/удаления временных БД и назначения владельца. Тестовой роли `CREATEDB` не требуется. Соединения закрываются, а созданные сценарием БД удаляются в `finally`, в том числе после ошибки проверки. Ошибки очистки не скрываются.

## Команды и защита

- `make migrate` — применить миграции к БД приложения.
- `make test-setup` — подготовить обычную тестовую БД.
- `make check-migrations` — подготовить тестовую роль и проверить оба сценария в новых временных БД.
- `make verify` — Ruff, SAST, тесты/покрытие, контрольные мутации и проверка миграций.

Отчёт `reports/migrations.json` содержит результат, цепочку ревизий, этапы обновления и количество сохранённых записей. При ошибке указывается тип исключения; команда завершается с ненулевым кодом.

Для контроля чувствительности проверки во временной копии в миграцию добавляется изменение имени продавца: чистая БД обновляется, но сценарий с данными должен обнаружить порчу записи. Другой контроль удаляет создание ожидаемого индекса: проверка схемы должна обнаружить расхождение. Контрольные изменения не попадают в репозиторий.
