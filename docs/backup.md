# Резервное копирование и восстановление

## Команды

| Команда | Назначение |
| --- | --- |
| `make backup` | Создать копию схемы и данных БД из `DATABASE_URL` в `backups/` |
| `make backup BACKUP_FILE=backups/demo.dump` | Создать копию по заданному пути, не перезаписывая существующую |
| `make restore BACKUP_FILE=backups/demo.dump` | Заменить объекты и данные из архива в существующей БД из `DATABASE_URL` |
| `make check-backup` | Проверить весь цикл во временной БД, включая ошибку повреждённого архива |
| `make verify` | Выполнить все обязательные проверки, включая `check-backup` |

Пути относительно проекта; пути с пробелами поддерживаются при корректном quoting в shell. Нужны pg_dump и pg_restore 14.20. Для обычных команд роль приложения должна иметь права чтения/владения восстанавливаемыми объектами. Для временной БД `check-backup` требуется административное подключение из `SETUP_DATABASE_URL` либо роль пользователя ОС с правами создания/удаления БД и назначения владельца.

## Что сохраняется

Custom-архив содержит схему, записи таблиц, ограничения, индексы, последовательности и ревизию Alembic. В копию входят аккаунты с хешами паролей, продажи, доходы и причины отклонения заявок. Конфигурация `.env`, исходный код и глобальные роли PostgreSQL не копируются. Для восстановления роль назначения и БД должны существовать; при необходимости их подготавливает `make setup`.

Владельцы и GRANT/REVOKE не переносятся: восстановленные объекты принадлежат роли назначения. `--clean` заменяет объекты, перечисленные в архиве, а не автоматически удаляет любые посторонние объекты БД. Восстановление старой копии может потребовать последующего `make migrate`.

## Порядок восстановления

1. Остановить приложение и проверить `DATABASE_URL`.
2. Указать собственный доверенный архив через `BACKUP_FILE`.
3. Выполнить `make restore BACKUP_FILE=...`.
4. При необходимости применить новые миграции и запустить приложение.

pg_restore проверяет оглавление архива до подключения и выполняет восстановление с `--clean --if-exists --single-transaction --exit-on-error`. При ошибке восстановление не оставляет частично изменённые объекты и записи. Отсутствующий файл или неправильный формат отклоняются. Пароль извлекается из параметров подключения и передаётся только в `PGPASSWORD` дочернего процесса, без включения в командную строку.

Новая копия сначала записывается во временный файл в той же папке; после успеха pg_dump и проверки формата публикуется под итоговым именем без перезаписи. Файл имеет права `0600`; новая папка — `0700`. Архивы и локальные отчёты не коммитятся.

## Автоматический сценарий защиты

`make check-backup` выполняет в отдельной БД `auctions_backup_<UUID>_test`:

1. Применить миграции до head и создать связанные записи во всех восьми таблицах, включая заявки и причину отклонения.
2. Создать custom-копию; проверить права файла и запрет перезаписи.
3. Изменить имя продавца и цены лотов, удалить доход и заявку с причиной; убедиться, что данные действительно отличаются.
4. Восстановить архив; точно сравнить все значения записей, ревизию Alembic и схему через `alembic.command.check`.
5. Проверить все восемь последовательностей: следующий ID больше сохранённого максимума.
6. Усечь архив, сохранив читаемое оглавление; восстановление должно завершиться с ошибкой. Проверить прежние записи, схему, ревизию и значения последовательностей.
7. Удалить временную БД и архивы, включая случай ошибки.

Отчёт `reports/backup.json` содержит итог, количество восстановленных записей и список проверенных последовательностей. Рабочая БД и данные обычной тестовой БД этим сценарием не повреждаются.

Для контроля чувствительности проверки во временной копии убирается `--single-transaction`: ошибка усечённого архива должна обнаружить частично восстановленное состояние и остановить `check-backup`. Контрольная подмена не попадает в репозиторий.
