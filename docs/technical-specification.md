# Техническое задание: «Аукционы»

## 1. Назначение и состав

Приложение ведёт учёт аукционов, лотов, участников, заявок на покупку, продаж и комиссии организатора. Пользователи работают через собственный веб-интерфейс (`/login`, `/app`); JSON API и Swagger UI (`/docs`) доступны отдельно. Сервер реализован на FastAPI, данные хранятся в PostgreSQL, схема изменяется миграциями Alembic.

## 2. Пользователи и веб-интерфейс

При первом запросе `POST /auth/login`, если в базе нет администратора, приложение создаёт его из `ADMIN_LAST_NAME`, `ADMIN_FIRST_NAME`, `ADMIN_MIDDLE_NAME`, `ADMIN_USERNAME` и `ADMIN_PASSWORD`. Пароль хранится как хеш PBKDF2-SHA256. Вход создаёт cookie-сессию; `POST /auth/logout` завершает её, `GET /auth/me` возвращает текущую учётную запись.

- **Администратор** создаёт учётные записи (`admin` или `user`), связывает пользователя с профилем продавца либо покупателя, создаёт аукционы, просматривает заявки, продажи и доходы, подтверждает или отклоняет заявки. Один профиль участника привязывается к одной учётной записи.
- **Продавец** видит свои лоты, заявки на них и продажи своих лотов; создаёт лот в существующем аукционе. Идентификатор продавца сервер берёт из учётной записи.
- **Покупатель** видит доступные лоты, свои заявки и продажи; отправляет заявку с предложенной ценой не ниже начальной.
- **Пользователь без профиля** может войти и увидеть аукционы; действия продавца и покупателя недоступны.

Кабинет показывает аукционы, лоты, заявки и продажи. Для администратора дополнительно открыты учётные записи, участники и доходы. Все предметные JSON-маршруты и `/web/*` требуют сессию пользователя. Управление участниками, создание аукционов, регистрация продаж и чтение доходов доступны администратору. Продавец читает свои лоты и продажи; покупатель читает доступные лоты и свои продажи. Ограничения действуют для списков и отдельных записей по ID. Без входа возвращается `401`, при недостаточных правах — `403`.

## 3. Основные сценарии и правила

1. Администратор создаёт аукцион с названием и датами начала и окончания. Даты должны содержать часовой пояс; окончание позже начала. Время приводится к UTC.
2. Продавец создаёт лот в существующем аукционе с положительной начальной ценой.
3. Покупатель отправляет заявку на доступный лот. Цена предложения не ниже начальной; одновременно допускается не более одной заявки со статусом `pending` на лот.
4. Администратор подтверждает заявку: в одной транзакции создаются продажа и доход, лот получает статус `sold`, заявка — `approved` и время рассмотрения. До подтверждения продажи нет.
5. При отклонении заявка получает статус `rejected` и время рассмотрения; лот остаётся доступным. Отклонённые заявки сохраняются в истории.
6. Один лот можно продать только один раз. Цена продажи не ниже начальной. Комиссия берётся из `COMMISSION_RATE` и округляется до копеек.
7. `GET /health` возвращает `{"status":"ok"}` при ответе приложения; соединение с PostgreSQL этим маршрутом не проверяется.

## 4. Модель данных

Схема состоит из восьми таблиц. Идентификаторы — первичные ключи; внешние ключи используют `ON DELETE RESTRICT`.

| Таблица | Основные поля и ограничения |
| --- | --- |
| `accounts` | `id`, ФИО (`last_name`, `first_name`, `middle_name`), уникальный `username`, `password_hash`, `role` (`admin`/`user`), необязательные уникальные `seller_id` и `buyer_id`, `created_at` |
| `sellers` | `id`, `name`, `created_at` |
| `buyers` | `id`, `name`, `created_at` |
| `auctions` | `id`, `name`, `starts_at`, `ends_at`, `status` (`planned`/`active`/`completed`), `created_at` |
| `lots` | `id`, `auction_id`, `seller_id`, `name`, `description`, положительная `starting_price`, `status` (`available`/`sold`), `created_at` |
| `purchase_requests` | `id`, `lot_id`, `buyer_id`, положительная `offered_price`, `status` (`pending`/`approved`/`rejected`), `created_at`, необязательная `reviewed_at` |
| `sales` | `id`, уникальный `lot_id`, `buyer_id`, положительная `final_price`, `sold_at` |
| `revenues` | `id`, уникальный `sale_id`, `commission_rate`, `amount`, `created_at` |

Продавец и покупатель связаны с учётной записью необязательно; их поля `name` не содержат email. Аукцион содержит лоты; лот принадлежит продавцу и может иметь несколько заявок, но максимум одну продажу. Покупатель может отправить несколько заявок и совершить несколько покупок. Каждая продажа имеет одну запись о доходе. Денежные поля хранятся как точные десятичные значения с двумя знаками после запятой. Временные отметки используют UTC.

## 5. Маршруты

| Область | Маршруты |
| --- | --- |
| Вход и страницы | `GET /`, `/login`, `/app`; `POST /auth/login`, `/auth/logout`; `GET /auth/me` |
| Исходный JSON API | `POST/GET /sellers`, `/buyers`, `/auctions`, `/lots`; `GET /sellers/{id}`, `/buyers/{id}`, `/auctions/{id}`, `/lots/{id}`; `POST/GET /sales`, `GET /sales/{id}`; `GET /revenues`, `/revenues/{id}` |
| Списки кабинета | `GET /web/auctions`, `/web/lots`, `/web/sales`, `/web/purchase-requests` |
| Администратор | `GET /web/revenues`, `/web/admin/accounts`, `/web/admin/sellers`, `/web/admin/buyers`; `POST /web/admin/accounts`, `/web/admin/participants`, `/web/admin/auctions`, `/web/admin/purchase-requests/{id}/approve`, `/web/admin/purchase-requests/{id}/reject` |
| Продавец и покупатель | `POST /web/seller/lots`, `POST /web/buyer/purchase-requests` |
| Служебные | `GET /health`, `GET /docs` |

Типовые ответы: `200` — успех, `201` — создание, `400` — нарушение бизнес-правила, `401` — требуется вход, `403` — нет нужной роли, `404` — запись не найдена, `409` — конфликт, `422` — ошибка валидации. Точные схемы запросов и ответов показывает `/docs`.

## 6. Среда, конфигурация и запуск

Локальное окружение: Python 3.12.5, PostgreSQL 14.20, uv 0.10.7. Версии инструментов указаны в `.tool-versions`, Python дополнительно закреплён в `.python-version`. Основные и dev-зависимости закреплены точными версиями в `pyproject.toml`; полный набор, включая транзитивные зависимости, закреплён в `uv.lock`. Диапазон совместимости Python: 3.12–3.13. Все команды Makefile используют `--locked`; `make quality` включает `uv lock --check`. Обновление зависимостей требует согласованного изменения `pyproject.toml` и `uv.lock` с последующим `make verify`.

Запустить PostgreSQL, выполнить `make setup`, затем `make run`. `make setup` устанавливает зависимости из `uv.lock` для Python 3.12.5, создаёт отсутствующий `.env`, роль и базу PostgreSQL и применяет миграции. Существующая конфигурация и данные сохраняются. Для создания роли и БД используется роль текущего пользователя ОС на том же сервере либо административное подключение из переменной окружения `SETUP_DATABASE_URL`; подробности приведены в README. Доступные команды: `make test`, `make quality`, `make format`, `make verify`. Для интеграционных тестов требуется доступная PostgreSQL с применёнными миграциями.

Переменные окружения: `DATABASE_URL`, `APP_HOST`, `APP_PORT`, `LOG_LEVEL`, `COMMISSION_RATE`, `SESSION_SECRET`, `ADMIN_LAST_NAME`, `ADMIN_FIRST_NAME`, `ADMIN_MIDDLE_NAME`, `ADMIN_USERNAME`, `ADMIN_PASSWORD`. До развёртывания заменить демонстрационные пароль администратора и секрет сессии. `LOG_LEVEL` считывается настройками, но сейчас не применяется для отдельной конфигурации журналирования. Локальный `.env` и рабочие секреты не сохранять в Git.

## 7. Приёмка изменений

Изменение структуры данных сопровождается миграцией Alembic. Перед включением изменений в основную ветку проект предусматривает `make verify`; проверки, тесты и документация должны соответствовать коду. Для проверки пользовательских сценариев следует проверить вход, назначение профиля, создание лота, подачу и рассмотрение заявки, появление продажи и дохода после подтверждения и отсутствие продажи после отклонения.
