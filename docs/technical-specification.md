# Техническое задание

## 1. Общая информация

Название проекта: «Аукционы».

Проект представляет собой HTTP API для учёта аукционов, выставленных лотов, продавцов, покупателей, продаж и доходов организатора.

## 2. Назначение системы

Система предназначена для хранения информации об аукционах и регистрации результатов продажи лотов.

Система должна позволять:

- создавать продавцов и покупателей;
- создавать аукционы;
- добавлять лоты на аукционы;
- регистрировать продажу лота покупателю;
- рассчитывать доход организатора от продажи;
- получать информацию об аукционах, лотах и продажах.

## 3. Категории пользователей

### 3.1. Администратор

Администратор создаёт аукционы, добавляет сведения о лотах и регистрирует результаты продаж.

### 3.2. Продавец

Продавец передаёт лоты для участия в аукционе и может просматривать информацию о своих лотах.

### 3.3. Покупатель

Покупатель приобретает лоты и может просматривать информацию о совершённых покупках.

## 4. Основные сценарии

### 4.1. Создание аукциона

Администратор передаёт название, дату начала и дату окончания аукциона. Система проверяет даты и сохраняет новый аукцион.

### 4.2. Добавление лота

Администратор выбирает аукцион и продавца, затем указывает название, описание и начальную цену лота. Система проверяет существование аукциона и продавца и сохраняет лот.

### 4.3. Регистрация продажи

Администратор выбирает лот и покупателя и указывает итоговую цену. Система проверяет возможность продажи, сохраняет сведения о продаже и рассчитывает доход организатора.

### 4.4. Получение информации

Пользователь запрашивает списки аукционов, лотов, продавцов, покупателей и продаж через HTTP API.

### 4.5. Проверка работоспособности

Система предоставляет служебный адрес `GET /health`. Успешный ответ означает, что приложение запущено и готово принимать запросы.

## 5. Сущности

### 5.1. Продавец

Поля:

- уникальный идентификатор;
- имя;
- уникальный адрес электронной почты;
- дата создания.

### 5.2. Покупатель

Поля:

- уникальный идентификатор;
- имя;
- уникальный адрес электронной почты;
- дата создания.

### 5.3. Аукцион

Поля:

- уникальный идентификатор;
- название;
- дата и время начала;
- дата и время окончания;
- статус;
- дата создания.

Допустимые статусы:

- `planned` — запланирован;
- `active` — проводится;
- `completed` — завершён.

### 5.4. Лот

Поля:

- уникальный идентификатор;
- идентификатор аукциона;
- идентификатор продавца;
- название;
- описание;
- начальная цена;
- статус;
- дата создания.

Допустимые статусы:

- `available` — доступен для продажи;
- `sold` — продан.

### 5.5. Продажа

Поля:

- уникальный идентификатор;
- идентификатор лота;
- идентификатор покупателя;
- итоговая цена;
- дата и время продажи.

### 5.6. Доход

Поля:

- уникальный идентификатор;
- идентификатор продажи;
- процент комиссии;
- сумма комиссии;
- дата создания.

Доход организатора рассчитывается на основании итоговой цены продажи и установленного процента комиссии.

## 6. Связи между сущностями

- один аукцион содержит несколько лотов;
- один продавец может выставить несколько лотов;
- каждый лот относится только к одному аукциону;
- каждый лот относится только к одному продавцу;
- один покупатель может совершить несколько покупок;
- одна продажа относится к одному лоту и одному покупателю;
- одна продажа создаёт одну запись о доходе;
- один лот может иметь не более одной продажи.

## 7. Обязательные правила

1. Дата окончания аукциона должна быть позже даты начала.
2. Начальная цена лота должна быть больше нуля.
3. Итоговая цена продажи должна быть не меньше начальной цены лота.
4. Один лот нельзя продать более одного раза.
5. Продать можно только существующий и доступный лот.
6. Продажа должна относиться к существующему покупателю.
7. Запись о продаже и соответствующая запись о доходе должны сохраняться в одной транзакции.
8. Денежные значения должны храниться как точные десятичные числа, а не как числа с плавающей точкой.
9. Даты и время должны храниться в часовом поясе UTC.

## 8. Обработка ошибок

API должно возвращать понятные ответы с подходящими HTTP-кодами:

- `400 Bad Request` — нарушено правило предметной области;
- `404 Not Found` — запрошенная сущность не найдена;
- `409 Conflict` — возникает конфликт, например повторная продажа лота;
- `422 Unprocessable Entity` — запрос не прошёл проверку структуры или типов данных;
- `500 Internal Server Error` — произошла непредвиденная внутренняя ошибка.

Ответ об ошибке не должен раскрывать пароли, строки подключения, трассировки и другие внутренние данные приложения.

## 9. Требования к хранению данных

- для постоянного хранения используется PostgreSQL;
- структура базы данных изменяется только через миграции Alembic;
- связи обеспечиваются внешними ключами;
- уникальность продажи лота обеспечивается ограничением базы данных;
- денежные значения хранятся с фиксированной точностью;
- операции создания продажи и дохода выполняются атомарно;
- строка подключения к базе данных задаётся переменной окружения;
- секреты и локальные файлы не сохраняются в Git.

## 10. Конфигурация

Приложение должно получать настройки из переменных окружения.

Минимальный набор переменных:

- `DATABASE_URL` — строка подключения к PostgreSQL;
- `APP_HOST` — адрес запуска приложения;
- `APP_PORT` — порт приложения;
- `LOG_LEVEL` — уровень журналирования;
- `COMMISSION_RATE` — процент комиссии организатора.

Репозиторий должен содержать файл `.env.example` только с примерами безопасных значений. Настоящий файл `.env` не должен попадать в Git.

## 11. Требования к качеству

Проект должен предоставлять единые команды:

- `make setup` — первоначальная настройка;
- `make run` — локальный запуск;
- `make test` — запуск автоматических тестов;
- `make quality` — статический анализ и проверка форматирования;
- `make migrate` — применение миграций;
- `make verify` — полный набор локальных проверок.

Перед включением изменений в основную ветку команда `make verify` должна завершаться успешно.

Запрещается удалять тесты, отключать проверки или ослаблять правила качества только ради успешного прохождения проверки.
